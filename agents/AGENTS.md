# AGENTS.md

Personal Claude Code subagent definitions. Each `<name>.md` file's frontmatter configures identity, tools, and model; its body is the agent's entire system prompt. The `create-claude-agent` skill (and its `references/agent-config.md` docs digest) is the authority on the frontmatter surface.

## How these agents are built

- **Thin agent + skill.** When a library skill already owns the methodology, the agent preloads it via the `skills` frontmatter field and the body carries only identity, tool limits, autonomous overrides, and the output contract. Methodology stays in one place; duplicating it into the agent body creates drift.
- **Autonomous overrides are the load-bearing section.** Library skills assume an interactive session; subagents cannot ask the user, post externally, or wait for approval. Each agent body explicitly rewrites the skill's "ask the user" steps as decide-and-disclose and its outward actions as return-only.
- **Reviewers and auditors get read-only tool allowlists** (`Read, Grep, Glob, Bash`) plus a body rule restricting Bash to inspection; an agent that can edit can "fix" what it was asked to judge.
- **Verification is spawn-by-path**: new agents do not appear in the session registry until reload, so they are tested by general-purpose subagents adopting the definition file, run against sandboxes with planted ground truth, twinned with no-definition baselines.

Each entry below carries only what the agent's own frontmatter description does not: wrapped skills, seams against sibling agents, and rationale for model or design choices.

## Agents

- `implementation-planner` - wraps `create-code-plan`; pinned to opus because plan quality bounds everything built from it.
- `plan-reviewer` - wraps `scrutinize` (method) + `create-code-plan` (rubric); opus for the same reason as the planner. Dispatched by `execute-code-plan` only for large or complex plans; small plans rely on create-code-plan's step 6 self-review.
- `product-spec-reviewer` - wraps `scrutinize` + `spec` (reads `references/product-spec.md` as the PRD rubric); scrutinize's code-trace pass is adapted to whether the requirements serve the stated problem, since a PRD has no code. Not auto-wired: the spec skill's authoring modes are interactive and the user reviews as they author.
- `tech-spec-reviewer` - wraps `scrutinize` (method) + `spec` (rubric via `references/tech-spec.md`); on-demand like product-spec-reviewer, opus.
- `code-reviewer` - wraps `review-pull-request`; adds an anti-noise discipline (80 percent confidence bar, pre-report gate, zero-findings-valid) because manufactured findings are automated review's primary failure mode. Inspects PRs via `git fetch pull/<n>/head` + `git show`, never `gh pr checkout`, so the spawning session's tree is untouched.
- `security-reviewer` - preloads `harden` as the rulebook, not the workflow (that skill is build-time; the audit methodology lives in the agent body). PoC bar for Critical/High severity.
- `task-implementer` - wraps `follow-tdd` + `code-with-best-practices`; a task that cannot be implemented honestly as written returns Blocked, never an invented premise (the skill's user-confirmed TDD exceptions become Blocked reports, since a subagent cannot ask). Does not commit unless told.
- `completion-verifier` - re-runs everything itself (a handed report is claims to audit, not facts) and exists to catch the green-suite-but-unmet-requirement case, including its wiring analog: code present and green but imported and called by nothing. Shares the task-implementer's report shape so the two compose.
- `root-cause-investigator` - wraps `fix` but runs only through step 4; stops at the confirmed root cause so the main loop keeps the failing-test-first fix workflow. The one agent allowed to mutate the tree (instrument, bisect), contractually required to restore it before returning.
- `deep-researcher` - self-contained (no wrapped skill); cannot spawn sub-subagents, so it researches sequentially and is the dispatchable building block complementary to the bundled `/deep-research` main-loop harness.
- `silent-failure-auditor` - self-contained; carries code-reviewer's anti-noise discipline (quote gate, intentional-suppression-is-not-a-finding, zero-findings-valid, variant sweep) because manufactured findings are its failure mode. A lens no pipeline agent owns: code-reviewer is general, security-reviewer is exploitability, root-cause-investigator runs only after a failure has surfaced.
- `manual-tester` - wraps `validate-web` + `validate-api`; pinned sonnet because semi-manual driving and evidence capture is focused single-domain work. Autonomous overrides turn the skills' "ask for the URL / install the CLI" stops into derive-or-start-or-Blocked (a missing CLI is a Blocked report naming the install command, never a silent global install); the only files it writes are validation artifacts.
- `test-writer` - wraps `follow-tdd` + `code-with-best-practices`; because the code already exists, follow-tdd's Iron Law adapts to a can-fail check (a test that cannot fail is fixed or dropped). A bug the tests expose is a reported Finding, never fixed in production source or loosened into green; model inherited because edge-case selection is implementation-grade judgment.
- `agent-context-auditor` - wraps `audit-agent-context`; the skill's offer-to-apply-fixes and route-to-onboard/tune-context steps become recommend-only. Audits the docs-about-the-code, a lens none of the code or spec reviewers own.
- `test-coverage-requirement-auditor` - wraps `follow-tdd` as the coverage rubric only (golden/error/edge floor, can-fail bar); runs the suite read-only so Uncovered is distinguishable from currently-failing. Writes no tests; recommends dispatching test-writer for the gaps.
- `architecture-auditor` - wraps `audit-architecture`; the skill's offer-to-implement and route-to-create-code-plan steps become recommend-only. Carries code-reviewer's anti-noise discipline because manufactured tech-debt is its failure mode.
- `performance-optimizer` - wraps `optimize-performance` + `code-with-best-practices`; the one profiling doer. A change it cannot show improves a measurement is reverted, and existing tests must be green before and after.
- `code-refactorer` - wraps `refactor` + `code-with-best-practices`; a bug it finds is an Observation, a needed behavior change is a Blocked report, never made silently. Green before AND after, no test loosened to pass.
- `maintainability-reviewer` - wraps `refactor` as rubric only (its opportunities table + first-rung ladder, NOT its mutating Test-Gate workflow, which `code-refactorer` runs); guards against dogmatic SOLID/DRY and speculative generality, its failure modes, with a "name the cost, metrics never a verdict" bar. Seam vs `architecture-auditor`: intra-module cost-of-change within the change; it defers module-level coupling and mock-five-collaborators findings to the auditor.
- `ux-reviewer` - wraps `audit-ui` scoped to its usability half only (Nielsen heuristics, interaction states, persona walkthroughs), explicitly excluding the anti-slop visual, typography, contrast, and WCAG dimensions, which it routes back to audit-ui. Heuristic not empirical, so it works from source or a described flow without rendering, and routes runtime confirmation to manual-tester.
- `design-contract-validator` - self-contained; deliberately NOT a soundness review (never judges whether the design is the right one; that is `tech-spec-reviewer`, routed in one line). Keeping the two lenses separate is what makes its report trustworthy on its own job.
- `test-case-planner` - wraps `follow-tdd` as the coverage rubric only; the dispatch target of the `generate-test-cases` skill. Its body carries an edge-case taxonomy walked per behavior to force breadth past the obvious, and follow-tdd's can-fail bar carries into planning: a case that could not fail if the behavior were broken is dropped.

## The pipeline

Seven of the twenty-two agents compose into plan -> review -> implement -> verify: `implementation-planner` produces the plan, `plan-reviewer` adversarially vets a large or complex plan before any task runs, `task-implementer` executes each task (parallelizable where the plan marks tasks independent; add `isolation: worktree` if they would collide), `completion-verifier` gates each checkpoint, `code-reviewer` + `security-reviewer` do the final pass, and `root-cause-investigator` is the off-ramp when something breaks. The remaining fifteen sit outside the pipeline: `product-spec-reviewer`, `tech-spec-reviewer`, and `design-contract-validator` are the on-demand spec-stage gates before any plan exists (the first two apply the adversarial soundness pass to the PRD and the system design; design-contract-validator runs the orthogonal completeness-and-implementability check, can it be built without guessing); `deep-researcher` is an independent multi-source research specialist dispatchable from any skill or the main loop; `silent-failure-auditor` is an on-demand error-handling auditor for changes that touch failure paths; `agent-context-auditor` checks the AGENTS.md set against the code and the contextual-documentation standard; and `test-case-planner`, `test-writer`, `test-coverage-requirement-auditor`, and `manual-tester` are the testing specialists: test-case-planner enumerates the case matrix before any test is written (dispatched by the `generate-test-cases` skill), test-writer backfills automated regression coverage for code already written, test-coverage-requirement-auditor audits an existing suite for requirement-coverage gaps without writing anything, and manual-tester is the live-confirmation step once the suite is green (the validate in red-green-refactor-validate). Five more are on-demand build specialists: `architecture-auditor` is a read-only structural audit, `maintainability-reviewer` and `ux-reviewer` are two read-only review lenses the pipeline's final pass can add alongside code-reviewer and security-reviewer, and `performance-optimizer` and `code-refactorer` are the two editing doers dispatchable for isolated optimization or behavior-preserving cleanup (worktree-isolate them when run in parallel). The `execute-code-plan` skill is the thin orchestrator that drives this from the main conversation (it spawns these agents, so it cannot itself be an agent); the agents already speak compatible output contracts, which is what keeps it thin.

## Gotchas

- Agent `description:` frontmatter must use a `>-` folded block scalar (or contain no `: ` sequence). An unquoted colon-space anywhere in a plain scalar makes the YAML frontmatter fail to parse, and Claude Code silently drops the agent from the registry with no error; this happened to five agents undetected.
- `harden` explicitly excludes auditing ("use the bundled /security-review"); the security-reviewer agent is the library's own audit surface and reframes the skill as its checklist. Do not "fix" the agent by pointing it at a nonexistent audit skill.
- Spawn tests showed strong opus baselines reach near detection parity on planted bugs; these agents earn their place through format consistency, scope discipline, and hard guardrails (no posting, no tree mutation), not raw detection. Judge future agents the same way.
- Verifier-type agents need a genuine-work control in their spawn test, not just a planted-defect case. A verifier that rejects everything passes the defect case for the wrong reason; `completion-verifier` was tested against both a doctored copy (must Reject) and a real completion (must Verify) to prove it discriminates rather than always-rejects.
- Interrogation/interview skills cannot become agents. `AskUserQuestion` is one of the tools the official docs list as unavailable to subagents (alongside `Agent`, `EnterPlanMode`, `ScheduleWakeup`) "even when listed in the `tools` field", and the docs route "frequent back-and-forth or iterative refinement" to the main conversation. Skills built on a live one-question-at-a-time interview with a user yes-gate (`spec`, `interrogate`) stay skills; wrapping them as agents silently drops the interview, which is their entire value. The decide-and-disclose pattern only substitutes for clarification the agent can resolve from material it was handed, never for eliciting intent that lives only in the user's head. Reviewing is the exception that proves the rule: `product-spec-reviewer` and `tech-spec-reviewer` preload `spec` and read its product-spec / tech-spec references as a rubric (what a sound spec must contain), which is legitimate precisely because a reviewer reads an existing spec and never interviews. The prohibition is on wrapping these skills as authoring agents, not on using them as a review checklist.
- `deep-researcher` researches sequentially; it cannot fan out to sub-subagents (the no-sub-subagent rule). To widen coverage, dispatch several from the main loop, one per sub-question, and synthesize their reports.
